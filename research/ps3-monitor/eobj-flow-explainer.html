1. General mechanism, asset-specific meanings

The client does not have a universal “Sastasha animation enum.” It has a general 16-slot shared-group timeline mechanism. A 16-bit value selects slots. The loaded asset defines which timeline belongs to each slot.

Engine convention general

Slots 0–15. Slot i is selected by 1 << i. The client can test, play and stop that slot.

Asset configuration per SGB

Each slot maps to a timeline MemberID. For this grate, slot 0 maps to the timeline named open.

Gameplay policy per encounter/script

The server decides when to select those timelines, whether an interaction is allowed, and whether enemies should spawn.

Your constants are useful human-readable names for this asset’s slots:

// A convenient server-side naming scheme, not a recovered global enum.
namespace SastashaGrate {
  constexpr uint16_t Open   = 1 << 0; // 0x0001
  constexpr uint16_t Close  = 1 << 1; // 0x0002
  constexpr uint16_t VfxOn  = 1 << 2; // 0x0004
  constexpr uint16_t VfxOff = 1 << 3; // 0x0008
}
More precise than “per dungeon”: the mapping is per shared-group asset. Different objects in one dungeon can use different SGBs and therefore different meanings for 0x0001. Multiple placed instances—or multiple territories—can reuse one SGB and share its mapping.

For an unrelated asset, slot 0 could mean something entirely different, or be disabled. The engine knows “slot 0”; it does not infer “open a grate” from the bit itself.

What “EXD format” means here

Think of EXD as a collection of typed spreadsheets stored in binary form. root.exl is a catalog. An .exh describes the layout of a sheet, and its .exd pages carry the rows. The schema contains physical types and offsets, not necessarily friendly names or complete foreign-key semantics.

exd/root.exl
  └─ EObj
      ├─ eobj.exh                  column layout, pages, languages
      └─ eobj_2000000_en.exd        English rows in this page
          └─ row 2000405           metadata for one unnatural-ripples EObj

In the PS3 row we decoded, EObj[2000405] includes the name “unnatural ripples,” an EventHandler value of 0x000F0043, and a SharedGroup value of 0. It also has visibility/pop/target-related fields. It does not contain the four timeline-mask constants.

Binary-file layout is not the same thing as the in-memory C++ layout

In PS3 EXH v3, columns refer to offsets in fixed row data. String cells contain offsets into a string pool. Packed boolean columns can share one byte. Multi-key rows include subkeys and share a string pool after all their fixed subrecords.

The PS3 numerics we decoded are big-endian. Loading may resolve strings, cache rows and construct runtime objects. A stored string offset is not a live host pointer. Likewise, PS3 DWARF struct offsets are not automatically valid in the Windows client: pointer sizes and class layouts differ.

The relevant PS3 EObj fixed data is 32 bytes, but the live EventObject is a separate class containing many additional runtime fields. The mask is a field of that live object, not an extra column hidden in the EObj sheet.

4. How the files meet the network object

There are two streams that converge: loaded visual assets and the server’s live EObj description. This is a dependency diagram, not a claim that all I/O happens synchronously in this exact order.

  1. The client identifies the territory’s level assets.

    In the monitor data, TerritoryType row 157 points to level name/path s1d1 / ffxiv/sea_s1/dun/s1d1/level/s1d1. The corresponding LVB references level groups including bg.lgb.

  2. The layout engine loads placed shared groups.

    The Sastasha bg.lgb contains the bound grate IDs listed above. Each of those placements references sgbg_s1d1_m1_bos1.sgb. The SGB supplies child assets, settings and authored timelines.

  3. Shared-group settings become runtime slot mappings.

    The asset’s GeneralPurposeTimelineIDs[16] is copied into the live shared-group instance. Timeline records become timeline instances which the scheduler can play. On Windows, the slot-ID array is at shared-group +0x168.

  4. A CreateObject message describes a live EObj.

    The packet carries values including BaseId, EntityId, LayoutId, BindLayoutId, position and Args2. The client creates/sets up its EventObject and looks up EObj metadata by BaseId.

  5. The EObj binds to the visual shared group.

    For these grates, BindLayoutId supplies the connection to the existing placement. This is why an EObj row with SharedGroup = 0 can still control a shared-group asset.

  6. The initial stored timeline mask comes from Args2.

    The mapped CreateObject handler passes the low 16 bits of Args2 to SetSharedGroupTimelineState. The setter stores the mask first, then checks whether the asset/layout is ready for playback.

  7. Later server messages update the state or playback.

    The client uses the already-loaded/cached metadata and asset instances. The setter does not reopen the EXD/SGB from disk every time the server changes a mask.

What if an EObj is not bound to an existing placement?

The PS3 EventObject setup code also has a path that looks up ExportedSG metadata using the EObj row’s SharedGroup value. That provides an asset reference for creating a shared group instead of relying on an existing bound layout placement. The bound Sastasha grates take the placement-based route.

These are alternate ways to obtain the visual group. Once the live shared group exists, the same general slot/mask mechanism can be used.

Loading/readiness matters. A cached mask and an executing animation are not the same thing. The setter can store the new mask before the shared group is ready, with no immediate playback. Initializing/reapplying state must account for readiness; “a packet was sent” does not alone prove that a visible effect has already started.

The asset bytes are 0C 0E 0F 10 00 …, not a list of 01 02 04 08 flags. The flags follow from the engine’s 1 << slot rule. In the PS3 SGB structure, this sixteen-byte mapping starts at SGSettings + 0x05.

A MemberID is also not the same thing as the separate SGTimeline_t::TimelineID field: those TimelineID values are zero in this asset. The slot dispatch resolves the member mapping.

What is inside a timeline?

Below the general-purpose slot API, the scheduler plays authored content affecting members of the group. Such content can animate geometry, control effects or involve sound. The grate asset contains embedded timeline data and references to grate models, a VFX resource and opening/closing/water-splash sounds.

We recovered the timeline names and slot mapping; we have not exhaustively decoded every clip’s exact effect lifetime or collision behavior. The names are useful evidence, but they are not a substitute for tracing every authored clip.

“Off” is an authored timeline, not a negative bit. Selecting vfx_off means selecting slot 3. Clearing slot 2 asks the engine to stop that timeline if it is playing. Those are distinct operations. Do not assume that stopping a timeline reverses every effect it previously created.

6. Three network commands that look similar

These numbers are ActorControl IDs inside the Order message, not the outer IPC packet opcodes. In particular, an outer CreateObject opcode named 0x019D is not the same dispatch layer as ActorControl 0x19D.

ActorControl IDArgumentsClient behavior
0x199
SetSharedGroupTimelineState		arg0 = stored maskCalls the EventObject setter. Saves old state, writes new state, then follows the handler or fallback playback path.
0x19A
Single timeline play		arg0 = slot index
arg1 = start time		Uses the single-slot GameObject playback wrapper. This is not the mask setter.
0x19D
PlaySharedGroupTimeline		arg0 = stored mask
arg1 = playback mask		Directly reconciles the 16 playback slots against arg1, then writes arg0’s low 16 bits into the EventObject state field.

The two masks in 0x19D can differ. If arg0 is 0x000A while arg1 is 0x0004, the object’s stored state says close + VFX-off, while the direct playback request selects VFX-on. The client code permits that distinction; gameplay code should decide whether it actually wants it.

// Existing Sapphire API in this checkout:
eobj.playSharedGroupTimeline(flag, animationFlag);
// Sends ActorControl 0x19D:
//   first parameter  → arg0 → stored timeline state
//   second parameter → arg1 → playback selection
// Neither parameter is the separate getState() spawn Flag byte.
For a simple “stored state should match what I request to play” operation, the two masks would normally agree. That is a server API design decision, not a requirement imposed by the client’s packet format.

7. What happens inside the setter?

Windows 0x1409EC750 corresponds to PS3 0x0097A850. The following is a simplified explanation of its behavior, not a literal source reconstruction:

oldState = eventObject.timelineState;
eventObject.timelineState = newState; // uint16; Windows +0x1A2

if (playbackDisabled || !sharedGroup || !sharedGroupReady)
  return; // the stored state has already changed

if (checkLayoutReady && !terrainAndSceneReady)
  return;

if (objectHasAnOwningEventHandler)
  handler.onSetSharedGroupTimelineState(oldState, newState, ...);
else
  reconcileEnabledSlotsWith(newState);

A. No owning handler: reconcile against the new mask

For each enabled slot: if its bit is set and it is not playing, play it; if its bit is clear and it is playing, stop it. This compares the request to the current playback status, not just old state to new state.

B. Base event handler: react to changed bits

changed = oldState ^ newState;
rising  = changed & newState;   // bits that turned on
falling = changed & ~newState;  // bits that turned off

// For enabled slots:
// rising bit  + not already playing → play
// falling bit + currently playing   → stop

The base callback is Windows 0x140652F30 / PS3 0x0098D228. It also performs event-scene rollback bookkeeping.

Derived handlers can change the policy. We observed a PS3 quest override that plays rising bits, and a Windows override with additional mask handling. We have not established the exact owning-handler subclass/replay policy for every Sastasha interaction.

C. Direct 0x19D: reconcile against its playback mask

The Order branch asks the GameObject wrappers to play/stop each slot according to arg1, then stores arg0. It does not call the setter’s old/new handler callback path for that update.

Why the same value can behave differently: sending 0x0004 → 0x0004 gives the base handler no rising bits. If a one-shot timeline already finished, it may not replay there. The no-handler fallback or direct playback-mask path can ask to play the selected slot again when it is no longer playing. A stored mask is not an “animation is still running” flag.

The useful Sastasha transition

old = 0x0004  // slot 2: vfx_on
new = 0x000A  // slots 1 and 3: close + vfx_off

rising  = 0x000A // select close and vfx_off
falling = 0x0004 // deselect vfx_on

This explains why your code replaces the mask with Close | VfxOff. Merely OR-ing in VfxOff would produce 0x000C, leaving the VfxOn bit selected too.

9. What this means for Sapphire code

Keep at least these concepts separate

ConceptWhere it belongsHow to think about it
Object state byte
getState() / spawn Flag		Existing Sapphire EObj state field.A separate field. Do not reinterpret every existing state comparison as a shared-group timeline-mask comparison.
Stored timeline mask
timelineState		Client EventObject; a server implementation should deliberately mirror its intended value.A 16-bit selection/state value. Initial CreateObject Args2 and later control messages must be consistent with the server’s chosen contract.
Requested/current playbackClient scheduler and, for 0x19D, a distinct packet argument.Selected slots, running timelines and resulting persistent visuals are not necessarily identical.
Gameplay stateEncounter/script logic.Whether the grate is dangerous, an interaction succeeded, or an enemy should spawn. Use explicit server logic rather than assuming every visual bit proves gameplay state.

In this checkout, EventObject::spawn() sends Args2 = 0, and the class has playSharedGroupTimeline() but not the getAnimation()/setAnimation() methods from your example. Therefore a full implementation needs intentional mask storage and synchronization, not just a condition-parser change.

Use bit conditions for bit questions

// Specific slot selected, even if other slots are selected too:
const bool vfxOnSelected = (state & SastashaGrate::VfxOn) != 0;

// All requested slots selected:
const bool closeAndOffSelected =
  (state & (SastashaGrate::Close | SastashaGrate::VfxOff)) ==
           (SastashaGrate::Close | SastashaGrate::VfxOff);

// A genuinely exact state question still uses equality:
const bool exactlyCloseAndOff = state == 0x000A;

For example, state == 0x0004 is false when state is 0x0006, but (state & 0x0004) != 0 is true. The second expression correctly asks whether that slot is selected.

Use hasAny, hasAll and hasNone deliberately; they are different predicates. In particular, hasAll(state, 0) is always true. Use exact equality if you mean “the mask is zero.”

A practical implementation checklist

  1. Give the server’s timeline-mask field an explicit name and width; do not silently reuse the EObj state byte.
  2. Keep descriptive constants near the script/asset mapping, not in a global enum that implies every bit has the same action everywhere.
  3. Decide which update path the API uses: the setter path, the single-slot path, or the direct stored-mask/playback-mask path.
  4. When an API means “set the desired selection,” update the server’s cached mask and send arguments consistent with that intent.
  5. Initialize CreateObject Args2 from the cached mask so later-arriving players receive the current intended state.
  6. Test existing players, late arrivals, asset readiness, repeated identical updates and combined-bit values.
  7. Track gameplay state separately if the encounter needs stronger facts than “a client timeline slot was selected.”
The client timeline does not itself implement your server’s boss AI. Sending vfx_on is not a replacement for scheduling an add spawn; sending a log message is not the same operation as changing a visual group.
There are several things called “timeline”

Sapphire encounter timelines schedule server gameplay operations. SGB general-purpose timelines are client visual/scheduler content selected by these slots. Character action timelines are another system again. Their shared name does not make them one data format or one state variable.
